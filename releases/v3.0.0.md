# Conlab v3.0.0 Commenting MVP

Conlab v3.0.0 adds governed discussion comments to the controlled collaboration text ledger.

This release keeps the v2 GenAI-supported workflow and adds a lightweight review feedback loop around every event log entry.

## What Is New

- Discussion comments on existing event log entries
- Comments can be added to content, questions, decisions, and other visible event records
- Comments are stored as ledger events in `conlab.json`
- Comments do not alter the rendered bucket text
- Seen marks for comments using a thumbs-up action
- Seen counts on comments so authors and reviewers can see acknowledgement
- One seen mark per user per comment
- Per-bucket `Unseen Comments` view for comments from other users not yet marked seen
- Compatibility hardening for legacy or partial event records
- Sidebar layout containment for long bucket names, descriptions, and repository labels

## Existing Features Kept From v2.0.0

- Git-backed workspace storage through `conlab.json`
- GitHub and GitLab repository support
- Repository role mapping into Conlab roles
- Content buckets and prompt buckets
- Review-required and auto-accept bucket modes
- Content create, revise, and delete event actions
- Questions and decisions
- Markdown rendering
- Rendered bucket text history navigation
- Markdown export of visible rendered bucket state
- GenAI contribution plausibility checks for content buckets
- Prompt buckets for reusable GenAI prompts
- Narrative generation from selected prompt and content buckets
- In-app polling notification for remote workspace updates
- Tauri macOS desktop packaging path

## Comment Workflow

Each event card can receive comments. A comment is useful when a contributor or reviewer wants to add context, ask for clarification, or leave feedback without changing the controlled bucket text.

Comments are intentionally separate from rendered content:

- they are visible in the event log
- they retain author and timestamp
- they are saved to Git as normal ledger entries
- they are excluded from rendered bucket text
- they are excluded from Markdown export of the current visible bucket text

## Seen Marks

Users can mark a comment as seen with the thumbs-up action.

The seen mark is also stored as a ledger event. This keeps acknowledgement auditable without mutating the original comment.

Rules:

- a user can mark each comment seen once
- the comment displays the total seen count
- seen marks do not affect rendered bucket text

## Unseen Comments View

Each bucket has an `Unseen Comments` section.

It lists comments that:

- were written by another user
- belong to the selected bucket
- have not yet been marked seen by the current user

This gives reviewers and contributors a compact queue for discussion items that still need acknowledgement.

## Data Model Notes

V3 introduces two additional event kinds:

- `Comment`
- `Reaction`

`Comment` events reference their target event through `baseEventId`.

`Reaction` events currently use `body: "seen"` and reference the comment event through `baseEventId`.

Older workspaces are still treated defensively. Missing event kind, status, body, comment, author, action, or timestamp values are normalized before rendering.

## Desktop Packaging

Build the macOS bundle with:

```bash
make desktop-build
```

Generated artifacts are written under:

```text
src-tauri/target/release/bundle/
```

Ad-hoc signed `.dmg` builds can be uploaded directly to GitHub Releases for MVP distribution. macOS may show a Gatekeeper warning on first launch because the app is not Apple-notarized.

## Install

For local browser usage:

```bash
make run
```

For desktop bundle creation:

```bash
make desktop-build
```

## Known Limitations

- No automatic app updater yet. New versions are installed by downloading the next `.dmg` and replacing the old app.
- Desktop builds are ad-hoc signed but not Apple-notarized.
- Tokens and GenAI keys are stored locally in browser/app local storage.
- Comment seen marks are simple acknowledgement signals, not threaded review states.
- Narrative generation output is copy-out only; it is not persisted as a new ledger event yet.
- No shared/cloud BFF is included.
